# 变更检测基准（不是标准答案）

## 这里的东西是什么

三台 1.0 臂（`OAF26062401` / `OAF26080401` / `OAF26090301`）在真机上跑完整流程留下的
记录，以及工作站当时对它们给出的放行判定和出厂报告。

**它们的作用只有一个：改代码之后，告诉我"输出变了"。**

## 它们不是什么

**不是判定对错的依据。** 它们是 2026 年 5–9 月按当时的流程、当时的官方版本
（openarm_can 1.2.2）测出来的。流程会改进，官方会更新，这些数字会过时。

**不是设计约束。** 如果按官方做法改动测试流程会让这些输出变化，那就**让它变**，
刷新基准、审 diff、记进 changelog。基准让路，不是流程让路。

## 权威次序

判断"什么是对的"时，按这个顺序：

1. **官方**——`docs.openarm.dev` 的文档 + `enactic/openarm_can` 的代码和 issue。
   两者都要查：硬件参数常常只在 examples 代码里，不在文档页。
2. **真机实测**——电机自己报出来的值。例：DM4340 的 VMAX 到底是 8 还是 10，
   16 颗电机读回 10.0，这比任何表都硬。
3. **本目录**——只回答"和上次比变了没有"，不回答"对不对"。

三者冲突时，**不要**以本目录为准。

## 什么时候该刷新

只要变化是有意的，就刷新。不需要犹豫：

```bash
.venv/bin/python tests/golden/refresh_release_gate_baseline.py   # 放行判定
.venv/bin/python tests/golden/build_report_baseline.py           # 出厂报告全文
git diff tests/golden/                                            # 必须看一眼
```

**唯一的要求是看一眼 diff**，确认变的是你打算变的东西。基准存的是全文而不是哈希，
就是为了这个——哈希只能告诉你"变了"，全文能告诉你"变了什么"。

## 什么时候该换掉

以后有了按成熟流程、在 CAN-FD 下、用 POS_FORCE 测出来的 2.0 整臂记录，
**应该把基准换成那一批**，这三台 1.0 臂退成历史参照。

判断时机：当"这三台臂代表我们现在的做法"这句话不再成立时。

## 已经踩过的坑

基准里如果混进了**每次运行都会变的东西**，它就会天天误报，而人会养成不看 diff
直接刷新的习惯——那时它就等于不存在了。已经归一化掉的：

- 报告生成时刻 `Generated UTC`
- 工作站版本号（每次发版都变）

判据是：**这个值变化时，是否说明"有人改了什么"？** 不是的话就归一化掉。
